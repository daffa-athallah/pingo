# Import existing Evidence exports into Zetaris

This storage-only path consumes the actual exports generated by
`backend/scripts/batch_evidence.py`:

```json
{
  "source_file": "IMG_0001.PNG",
  "extraction": { "domain": "...", "summary": "...", "entities": [], "sensitive": false, "confidence": "high" },
  "receipt": { "requested_model": "gpt-4o-mini", "routed_model": "gpt-4o-mini", "provider": "openai" }
}
```

The first real import stored 30 screenshot Evidence records, 65 canonical
entities and 69 relationships. OMB Burger/IMG_8922 was proved first, followed by
29 inserts and one existing-record skip in the batch, with zero failures and
four entity-upsert updates. No original JSON or screenshot was changed.
The verified replay inserted nothing, skipped all 30 Evidence records, made no
entity updates and reported zero failures. Independent SQL counts confirmed
30 distinct screenshot Evidence IDs, 65 distinct linked entity IDs and 69 edges.

The original JSON is never rewritten, reclassified or sent to a model again.
Raw screenshots stay in the existing single unsorted `screenshot/` folder.
Zetaris receives canonical Evidence, Entity and EvidenceEntity records through
the existing repository and ingestion bridge, rather than raw laptop image paths.

## Explicit conversion

`app/ingestion/saved_evidence.py` validates the exact three-key export, current
Evidence Agent schema, canonical normalization, receipt and referenced image.
It rejects unsupported or noncanonical input instead of silently repairing it.

The export has no application Evidence ID or timestamp, so the import assigns:

- Evidence ID: `ev_` plus a deterministic SHA-256 prefix over the original source
  basename, image content hash and canonical extraction. Formatting, receipt
  field order and file modification time do not change this ID.
- Initial Evidence timestamp: the export JSON's filesystem modification time in
  UTC. This is export metadata, not a claimed screenshot capture time. Replays
  retain the immutable timestamp already stored with that ID, including after
  copying the JSON to another machine.
- Entity IDs and field mapping: the unchanged `evidence_bridge.ingest` function.
  Shopping identity is normalized domain/brand/name; other domains use
  domain/name/city. Mutable type/category/location descriptors do not define IDs.
- Links: the bridge's existing depicted relationship and confidence mapping.
- Provenance: source JSON/image checksums, assigned IDs/timestamps and original
  perception receipts are recorded in private, ignored import reports.

Evidence remains append-only. Identical replay is skipped. A materially changed
extraction creates a new observation ID; conflicting existing records are never
silently overwritten. Entities upsert by their canonical IDs. Existing original
JSON files and screenshots are not changed by any of these operations.

## Commands

Run from the repository root, using a JDK 11+ and the existing backend virtual
environment. Supply the path to your private Zetaris env file; never put real
credentials on the command line or in source.

```sh
export JAVA_HOME="$(/usr/libexec/java_home -v 11)"

# Validate the entire folder. No model calls, connections, or writes.
backend/.venv/bin/python backend/scripts/import_evidence.py plan

# Store and read back one real record first.
backend/.venv/bin/python backend/scripts/import_evidence.py \
  --env-file ../getting-started/.env.local first --file IMG_8922.json \
  --proof backend/runtime/imports/IMG_8922.storage-proof.json

# Import the complete validated dataset only after that storage proof succeeds.
backend/.venv/bin/python backend/scripts/import_evidence.py \
  --env-file ../getting-started/.env.local batch \
  --proof backend/runtime/imports/IMG_8922.storage-proof.json \
  --report backend/runtime/imports/screenshot-evidence-import.json
```

Optional `--input` and `--images` arguments select the actual JSON and unsorted
image directories. Defaults are `sample_data/evidence` and `screenshot`.

Every batch validates all inputs before its first write, verifies the persisted
first-record proof, then imports sequentially. Each graph is read back, including
exact Evidence, stable entity IDs, exact persisted edges and related-evidence
lookup. A final pass rechecks the batch and source JSON checksums. A failure stops
the batch and keeps completed records; use its report for reconciliation.

Counters distinguish inserted/skipped/failed Evidence, inserted entities and
entity-upsert updates. For a rerun, use a new report filename: reports are not
overwritten. Idempotent data replay retains the existing Evidence and edges.

## Scope of this proof

`real_evidence_storage_roundtrip` proves the real screenshot -> canonical graph ->
Zetaris -> repository readback path. It explicitly sets Open Loop/orchestrator
verification false. Importing historical Evidence does not require Nightshift
and does not invent or revise an intention. Open Loops remain owned by the
existing agent system. This storage proof does not mark the Activity map's full
agent integration as complete.

JDBC still has no multi-table transactions. The existing repository's compensation
and single-writer limitations apply; see `ZETARIS_INTEGRATION.md`. A successful
import is readback-verified, not a claim of distributed transactional atomicity.

```sh
backend/.venv/bin/python -m unittest backend.tests.test_saved_evidence -v
```
