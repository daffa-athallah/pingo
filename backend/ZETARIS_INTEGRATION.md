## Retrieval strategy

get_related_evidence uses a deterministic SQL join:

```
loop_entities -> entity IDs supplied by caller
entity IDs -> evidence_entities -> evidence
```

It honors domain, exclusions, distinct evidence IDs, newest-first ordering and
limit. get_related_entities joins entities that share persisted evidence, excludes
the input IDs, and honors domain/limit. Candidate loops match actual entity edges
or the current in-memory contract's domain fallback; INVALIDATED loops are
excluded. Active loops are OPEN/ACTIVE. There is no vector or fuzzy search.

The HTTP screenshot count is the number of distinct screenshot Evidence records
linked to an entity. It does not count folders or hardcode fixture counts.
Thumbnails are references, not an assumption that Zetaris can read laptop paths.

## Atomicity and failure handling

Actual driver metadata reports no JDBC transactions, no batch updates, and
transaction isolation 0. This implementation does **not** claim multi-table SQL
atomicity or call commit/rollback as if they were supported.

- save_evidence validates references, stages entity upserts and links, then
  inserts Evidence last. Existing Evidence and historical edges cannot be
  rewritten. Identical replay is skipped; conflicting replay is rejected.
- A single-process compensation journal restores previous entity/loop rows and
  removes newly staged rows/edges when a write fails. Historical Evidence is
  never deleted or updated.
- If an Evidence acknowledgement is lost, readback distinguishes an acknowledged
  commit from a known failure. An unknown outcome retains its graph and blocks
  further writes on that repository instance pending reconciliation.
- A failed compensation similarly reports possible partial state and blocks
  further writes. Reads remain available for diagnosis.
- `bootstrap.build_orchestrator` scopes the existing synchronous OpenLoopAgent
  apply operation, including save/update and all link calls, in that compensation
  unit. It neither changes model decisions nor holds a scope over model calls.
  Callers using the legacy factory directly must scope such multi-call writes
  themselves; the repository cannot infer the end of separate protocol calls.

Use **one app writer** for this MVP. Local threads are serialized, but external
processes can observe intermediate rows and concurrent independent writers are
not coordinated. Iceberg's per-table writes do not make the six-table graph a
transaction. This is a documented hackathon limit, not production atomicity.

## Screenshot JSON workflow when Nightshift is available

The existing 30 images remain in one unsorted `screenshot/` folder. No originals
were moved, renamed, categorized, or manually classified. Existing exports now
live in `sample_data/evidence`; use `import_evidence.py` for those three-key
exports, not the older version-1 envelope commands below. The following section
documents that separate optional perception/reasoning workflow; it must not be
used to repeat perception on the already generated dataset.

`recall_data.py` keeps exact returned model text, its parsed extraction, a
sanitized routing receipt, image hash, original basename, stable application ID,
and timestamp in a version-1 envelope. Files are private and ignored under
`backend/runtime/`. Invalid returned Evidence is preserved separately, not
silently repaired. Conversion uses the existing parse_evidence/ingest functions;
its location cleanup and domain/entity identity mapping are transparent. Original
JSON is never overwritten. Unsupported envelopes fail instead of guessing an
old schema. Existing valid output skips perception; mismatched output is rejected.

Configure credentials yourself in a private local env file. Keep the existing
model IDs and Nightshift routing. The commands below do not use a direct-provider
fallback. Explicit env files take precedence over the blank backend template.

First generate and prove exactly one record:

```sh
backend/.venv/bin/python backend/scripts/recall_data.py \
  --env-file ../getting-started/.env.local extract \
  --image screenshot/IMG_8922.PNG \
  --output backend/runtime/extractions/IMG_8922.json

backend/.venv/bin/python backend/scripts/recall_data.py \
  --env-file ../getting-started/.env.local roundtrip \
  --input backend/runtime/extractions/IMG_8922.json \
  --output backend/runtime/proofs/IMG_8922.roundtrip.json
```

The roundtrip uses the real existing Open Loop Agent, requires matching NVIDIA
and OpenAI receipts, preserves IDs and verifies the stored graph. If the agent
chooses no loop, the script reports that honestly rather than inventing one.

Only after the real one-record proof succeeds, prepare remaining images and
preview/import saved JSON. extract-batch is sequential and skips valid existing
outputs. The importer never invokes a model, validates inputs before writes,
requires a matching persisted first-record proof, and reports inserted Evidence,
updated entities, skipped Evidence, failed items, and inserted entities. It stops
on storage failure and preserves completed work.

```sh
backend/.venv/bin/python backend/scripts/recall_data.py \
  --env-file ../getting-started/.env.local extract-batch \
  --images screenshot --output backend/runtime/extractions

backend/.venv/bin/python backend/scripts/recall_data.py batch \
  --input backend/runtime/extractions --images screenshot --dry-run

backend/.venv/bin/python backend/scripts/recall_data.py \
  --env-file ../getting-started/.env.local batch \
  --input backend/runtime/extractions --images screenshot \
  --proof backend/runtime/proofs/IMG_8922.roundtrip.json
```

Then run the real stored-data reasoning flow. The explicitly chosen demo context
is a **synthetic calendar event**, not Calendar integration. Alternatively supply
`--context` with a JSON array of canonical ContextEvent records.

```sh
backend/.venv/bin/python backend/scripts/recall_data.py \
  --env-file ../getting-started/.env.local run \
  --proof backend/runtime/proofs/IMG_8922.roundtrip.json \
  --demo-context --output backend/runtime/proofs/IMG_8922.run.json
```

This calls the existing Open Loop Agent on stored Evidence, then the unchanged
orchestrator's Context/Critic flow. Actual RunResult/TraceEvents and receipts are
saved; no ZETARIS or model events are fabricated. A NO_MATCH or failed/missing
receipt remains incomplete. The Activity visualization is not changed here.

## Offline sample and HTTP API

Explicit `SAMPLE_MODE=true` selects the unchanged InMemoryLoopRepository and
scripted, clearly labeled synthetic fixtures. It starts no JVM, requires no
Zetaris JAR/account, and calls no Nightshift or external model. It is not a
production fallback. Production missing configuration fails instead of silently
using fixtures.

```sh
SAMPLE_MODE=true backend/.venv/bin/python backend/scripts/run_sample.py
SAMPLE_MODE=true backend/.venv/bin/python backend/scripts/serve.py
```

The FastAPI entrypoint exposes:

| Endpoint | Behavior |
| --- | --- |
| GET /health | Mode and actual repository implementation |
| GET /entities?domain=food | Stored entity projection and relationship-derived screenshot counts |
| GET /entities/{entity_id} | One stored entity or 404 |
| GET /loops | Active stored loops |
| GET /sample | Explicit offline fixture result; disabled in real mode |
| GET /integration-status | Real-proof/run readiness; pending until both actually succeed |
| GET /agent-events/{run_id} | Existing TraceEvent shape for the saved run, or labeled sample run |

This is a read-only data API; multipart uploads, Check-in feedback persistence and
multi-run trace history are not added speculatively. The frontend's centralized
api.ts exposes getEntities, getEntity, getOpenLoops, getAgentEvents, and
getIntegrationStatus. Daffa's page components and Activity visualization retain
their current fixtures until he chooses to consume those functions; no visual
redesign or silent replacement of his state management was done.

## Docker architecture

HOST / existing sponsor setup:

- Zetaris is the already-installed platform, reachable on host JDBC port 10000.
  Its supplied containers, config and lifecycle are separate from Recall Compose.
- Nightshift remains a host service at 127.0.0.1:8088/v1 when available.

RECALL DOCKER:

- FastAPI/Uvicorn backend binds to 0.0.0.0:8000 with one worker.
- Frontend builds the existing React app and serves it through Nginx; /api is
  proxied to the backend. Sample builds explicitly label Check-in as sample mode.
- The default Compose file is offline SAMPLE_MODE, requires no sponsor env file,
  driver mount or running sponsor services, and does not bundle them.

```sh
docker compose up --build
```

Open http://127.0.0.1:5175. Backend health is at http://127.0.0.1:8000/health.
Initial image/dependency builds need downloads; the built sample runtime was
also tested with Docker networking disabled. RECALL_FRONTEND_PORT and
RECALL_BACKEND_PORT can override host ports.

Real mode uses compose.zetaris.yaml as an explicit override. The JAR is mounted
read-only, not copied. Set container URLs to host.docker.internal, and match the
Mac UID/GID so the non-root container can read private proof artifacts. Keep
credentials in the env file, never on the command line. For example:

```sh
ZETARIS_JDBC_URL=jdbc:zetaris:lightning@host.docker.internal:10000 \
METERLESS_BASE_URL=http://host.docker.internal:8088/v1 \
RECALL_UID="$(id -u)" RECALL_GID="$(id -g)" \
docker compose --env-file ../getting-started/.env.local \
  -f compose.yaml -f compose.zetaris.yaml up --build
```

If using another instance/port, set those actual environment values. Do not use
localhost for a host sponsor service from inside the app container. Real-mode
startup requires an existing writable schema; it does not auto-create objects.
Do not print expanded real Compose configuration; validate with config --quiet.
